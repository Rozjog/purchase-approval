
# Purchase Approval — система согласования закупок

Purchase Approval — учебное веб-приложение на Django для учёта заявок на закупку, их согласований и принятых решений.

Проект развивается в рамках практических работ по технологиям разработки приложений на базе фреймворков.

## 1. Возможности приложения

Система позволяет:

- Просматривать сотрудников, заявки, согласования и решения.
- Открывать подробную страницу каждого объекта.
- Искать заявки по названию и контрагенту.
- Фильтровать заявки по сотруднику, статусу и минимальной сумме.
- Сортировать заявки по идентификатору, названию, сумме и сотруднику.
- Использовать пагинацию с сохранением параметров фильтрации.
- Просматривать статистику закупок.
- Работать с записями через Django Admin.
- Отменять и восстанавливать выбранные заявки через массовые действия Admin.
- Открывать заявки по уникальным текстовым URL (slug).
- Получать данные через Django ORM.

Создание и редактирование объектов предусмотрено через Django Admin. Отдельные пользовательские веб-формы для этих операций не реализованы.

## 3. Модели данных

В приложении используются четыре взаимосвязанные модели Django.

| Модель | Назначение |
|---|---|
| Employee | Сотрудники и их должности |
| Request | Заявки на закупку |
| Approval | Согласование заявок |
| Decision | Решения по согласованиям |

### Employee

Основные поля:

- `name` — имя сотрудника.
- `role` — должность.

### Request

Основные поля:

- `name` — название заявки.
- `amount` — сумма закупки.
- `contractor` — контрагент.
- `employee` — сотрудник, создавший заявку.
- `status` — статус заявки.
- `slug` — уникальный URL-идентификатор.
- `requires_director` — вычисляемый признак необходимости согласования директором.

Статусы заявок определены через `TextChoices`:

- Создана
- Одобрена
- Отклонена
- Отменена

Поле `requires_director` реализовано через `GeneratedField` и вычисляется на стороне базы данных.

Если сумма заявки превышает 250 000 рублей, значение поля равно `True`.

### Approval

Основные поля:

- `request` — согласуемая заявка.
- `employee` — ответственный сотрудник.
- `status` — статус согласования.

Метод `can_approve()` проверяет полномочия сотрудника:

- Руководитель отдела — заявки до 250 000 рублей включительно.
- Директор — заявки свыше 250 000 рублей.

### Decision

Основные поля:

- `approval` — связанное согласование.
- `result` — результат решения.
- `comment` — комментарий.

Метод `apply()` сохраняет результат решения и обновляет статусы связанного согласования и заявки.

Связи между моделями реализованы с помощью `ForeignKey`.

Для защиты связанных объектов от случайного удаления используется `on_delete=models.PROTECT`.

## 4. Django Admin

В практической работе №10 настроена административная панель Django.

В ней реализованы:

- Регистрация всех четырёх моделей.
- Русскоязычные названия приложений, моделей и полей.
- Настраиваемые столбцы через `list_display`.
- Поиск через `search_fields`.
- Фильтрация через `list_filter`.
- Сортировка через `ordering`.
- Пагинация через `list_per_page`.
- Редактирование отдельных полей через `list_editable`.
- Поля только для чтения через `readonly_fields`.
- Встроенные формы связанных объектов через `TabularInline`.
- Поиск связанных объектов через `autocomplete_fields`.
- Вычисляемые столбцы через `annotate()` и `Count()`.
- Массовые действия через `@admin.action`.
- Ссылки на публичные страницы заявок.

Массовая отмена и восстановление ограничены заявками без согласований, чтобы избежать некорректного изменения уже обработанных записей.

Административная панель доступна по адресу:

`http://127.0.0.1:8000/admin/`

Для входа необходима учётная запись сотрудника с правами доступа в Django Admin.

## 5. Django ORM

Доступ к данным выполняется средствами Django ORM.

Используются следующие методы:

- `all()` — получение объектов.
- `get()` — получение одного объекта.
- `filter()` — фильтрация.
- `exclude()` — исключение записей.
- `order_by()` — сортировка.
- `Q()` — составные условия поиска.
- `annotate()` — вычисляемые значения.
- `aggregate()` — агрегатные показатели.
- `Count()` — подсчёт записей.
- `Sum()` — вычисление общей суммы.
- `select_related()` — оптимизация связанных объектов.
- `Paginator` — постраничный вывод.

### Пользовательский QuerySet

Для модели Request создан собственный `RequestQuerySet` с методами:

- `created()` — созданные заявки.
- `approved()` — одобренные заявки.
- `rejected()` — отклонённые заявки.
- `cancelled()` — отменённые заявки.

Пример:

```python
from purchase_requests.models import Request

created_requests = Request.objects.created()
approved_requests = Request.objects.approved()

print(created_requests.count())
print(approved_requests.count())
```

Обычный вызов `Request.objects.all()` возвращает все заявки независимо от их статуса.

## 6. Slug и get_absolute_url()

Для каждой заявки формируется уникальный текстовый идентификатор `slug`.

Например, заявка «Закупка ноутбуков» может получить адрес:

`/requests/zakupka-noutbukov-2/`

Русские названия транслитерируются в латиницу с помощью библиотеки Unidecode.

Метод `get_absolute_url()` формирует адрес подробной страницы заявки через `reverse()`.

В приложении сохранены перенаправления со старых числовых адресов вида `/requests/2/` на адреса со slug.

## 7. Контекстный процессор

В файле `homepage/context_processors.py` реализована функция `purchase_context()`.

Она передаёт в шаблоны общие данные:

- `site_name` — название проекта.
- `requests_count` — актуальное количество заявок.

Количество заявок отображается в навигационном меню на страницах приложения.

Контекстный процессор зарегистрирован в `purchase_approval/settings.py`.

## 9. Статистика закупок

Страница `/requests/statistics/` показывает:

- Общее количество заявок.
- Общую сумму закупок.
- Распределение заявок по статусам.
- Распределение согласований по статусам.
- Сумму одобренных заявок.
- Количество заявок по сотрудникам.
- Пять самых дорогих неотменённых заявок.

Для формирования статистики используются `aggregate()`, `annotate()`, `Count()` и `Sum()`.

## Практическая работа №11. Формы в Django

В Purchase Approval реализованы пользовательские формы Django.

### Фильтрация

Класс RequestFilterForm наследуется от forms.Form.

Форма используется для поиска и фильтрации заявок:
- по названию и контрагенту;
- по сотруднику;
- по минимальной сумме;
- по статусу;
- с выбором сортировки.

Данные передаются через GET-запрос, проверяются методом
is_valid() и используются через cleaned_data.

### Создание и редактирование

Класс RequestForm наследуется от forms.ModelForm.

Пользователю доступны название заявки, сумма, контрагент
и сотрудник.

Создание выполняется методом POST после проверки формы.
Для редактирования используется параметр instance.

Начальный статус устанавливается автоматически.
Slug формируется моделью.

### Отмена заявок

Отмена выполняется POST-запросом с CSRF-защитой.

Статус заявки изменяется на «Отменена», запись не удаляется.

Редактирование и отмена доступны для созданных заявок,
у которых ещё нет согласований.

### Загрузка изображений

К заявке можно прикрепить изображение товара.

Файлы хранятся в MEDIA_ROOT, а путь к ним сохраняется
в поле ImageField модели Request.

Для загрузки используется request.FILES и
enctype="multipart/form-data".
